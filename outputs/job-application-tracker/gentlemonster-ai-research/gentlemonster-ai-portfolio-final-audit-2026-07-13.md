# GENTLE MONSTER AI Research & Exploration 포트폴리오 최종 감사

작성일: 2026-07-13  
공식 공고: https://www.iiccareers.com/ko/o/211450  
대상 페이지: `/ai-exploration`

## 결론

기존 페이지를 그대로 제출하는 것은 권하지 않는다. 실제 근거는 강했지만, 공개 포트폴리오가 내부 시스템 문서처럼 길었고 다음 문제가 있었다.

1. AHEYA와 IDOL이 하나의 하네스처럼 이어져 보여 실제 관계가 흐려졌다.
2. `판단 표면`, `기획 계약`, `기억 승격`처럼 작업자에게는 익숙하지만 채용담당자에게는 추상적인 표현이 많았다.
3. 파일 이름과 상태를 나열했지만, 파일 안에 어떤 판단이 적혀 있는지는 본문에서 바로 보이지 않았다.
4. 시스템 수와 단계 수가 강조돼 `무엇을 해결하려고 만들었는가`보다 구조 자체가 먼저 보였다.
5. 전체 분량이 길어 공고가 중요하게 보는 탐구 과정과 사고 방식이 오히려 묻혔다.

2026-07-13 개편본은 공개 포트폴리오를 여섯 장면으로 줄이고, 근거 저장소는 별도 상세 페이지로 남겼다. 이후 두 번째 개편에서는 첫 장면의 동일한 카드와 연대기 목록을 제거하고, AHEYA 콘텐츠에서 IDOL 제작 시스템으로 이어진 네 번의 전환점을 실제 화면과 함께 배치했다.

## JD 재해석

이 공고는 AI 연구자나 생성 툴 오퍼레이터를 찾는 공고가 아니다. 핵심 평가는 다음 순서로 보는 것이 타당하다.

| 우선순위 | JD가 실제로 보는 것 | 포트폴리오에서 보여줄 방식 |
| ---: | --- | --- |
| 1 | 변화하는 AI를 직접 탐색하고 실험했는가 | 새 기능을 어떤 문제에 적용했고 무엇이 달라졌는지 |
| 2 | 기술보다 경험과 가능성을 보았는가 | 콘텐츠, 서비스, 작업 경험으로 확장한 실제 시도 |
| 3 | 완성본보다 반복 과정이 남아 있는가 | 실패, 폐기, 보류 이유와 다음 수정 |
| 4 | 다양한 도구를 목적에 맞게 사용했는가 | 모델 우열표보다 역할 분리와 실제 활용 경계 |
| 5 | 인사이트를 팀이 다시 읽을 수 있는가 | 핵심 파일 발췌, 단계별 기록, 다음 기획 기준 |
| 6 | 브랜드 경험으로 번역할 감도가 있는가 | MUSINSA·ADSB를 별도 브랜드 근거로 연결 |

리테일·공간은 JD의 주요 적용 영역이지만 현재 완료 사례가 없다. 포트폴리오 실적으로 쓰지 않으며, 지원 후 확장 가능성 또는 면접 질문의 영역으로 남긴다.

## 최종 공개 구조

### Hero

`새로운 AI를 실제 제작에서 시험합니다.`

첫 화면은 INK 키프레임 자료를 사용한다. Workbench UI보다 실제 콘텐츠가 먼저 보여야 브랜드·콘텐츠 직무의 지원자로 읽힌다.

### 01. Trend to Test

기술 네 가지를 별도 카드로 나열하지 않는다. 다음 네 번의 전환점 안에서 각 기술이 왜 필요했고 작업 방식이 어떻게 바뀌었는지 보여준다.

1. AHEYA 마케팅 콘텐츠에서 맥락 기반 LLM과 이미지 API를 시험한 출발점
2. Aurora의 26개 제작 단위에서 얼굴 유지와 반복 생성 가능성을 확인한 과정
3. Root Signal·LOW·Pulso·Left In That Night를 거치며 편집 보조와 기획 실패를 구분한 과정
4. INK와 Workbench에서 레퍼런스·보류 이유·기획 맥락을 다음 제작까지 이어간 현재 구조

각 전환점은 `당시 질문 -> 시도 -> 막힌 지점 -> 다음 변화`와 실제 화면으로 구성한다. 이 구간은 이야기의 역할을 맡고, 뒤의 IDOL·AHEYA 파일 발췌는 검증 자료의 역할을 맡는다.

### 02. IDOL Production System

AHEYA와 분리된 영상 제작 하네스로 명시한다. 일곱 단계와 자동화/사람의 판단 경계만 공개하고, Workbench 화면과 아래 세 파일의 핵심 내용을 직접 보여준다.

- `workbench-checkpoint.md`
- `stage-registry.yaml`
- `idol_video_source_intake.py`

### 03. INK

현재 공개 영상 한 편과 세 개의 판단 자료만 사용한다.

- 곡 전체 흐름을 보는 keyframe sheet
- 움직임 후보를 비교한 board
- 오브젝트 재사용 기준

LOW와 Left In That Night는 실패 이미지를 늘어놓지 않고 `왜 중단했고 무엇을 바꿨는가`만 제시한다.

### 04. AHEYA

콘텐츠 제작 흐름이 아니라 별도 서비스·신뢰 실험으로 설명한다. 스마트계약과 Yui 실행 구조의 핵심 두 파일만 본문에 발췌한다.

### 05. Archive & Learn

원본 기록 -> 실제 결과 대조 -> 다음 기준의 세 단계로 단순화한다. TikTok/X 공개 신호는 콘텐츠 판단의 참고 자료이며 전환이나 인과 성과로 쓰지 않는다.

### 06. Role Fit

공고 문장을 반복하지 않고 요구사항과 직접 근거를 한 줄씩 연결한다. MUSINSA와 ADSB는 AI Exploration 하네스의 사례가 아니라 별도 브랜드 콘텐츠 근거로 링크한다.

## 파일 공개 기준

파일처럼 보이는 모든 블록은 공개 방식을 함께 표시한다.

| 표시 | 의미 | 적용 자료 |
| --- | --- | --- |
| `원문 일부` | 실제 원문에서 공개에 필요한 행만 선별 | Workbench 주장 기준, IDOL 단계 레지스트리 |
| `편집 발췌` | 실제 코드에서 반복부·내부 경로·식별 정보를 덜어낸 발췌 | Python 움직임 분석, AHEYA 스마트계약, Yui 실행 흐름 |
| `구조 요약` | 원본의 핵심 관계를 공개용 문장으로 다시 쓴 자료 | 나머지 상세 근거 페이지 |

Yui 발췌에서는 인증 교환, 접근 토큰, 지갑 식별 필드, API 주소, 최종 기록 요청 본문을 제외했다. 스마트계약 발췌에서는 실제 주소, 배포 정보, 거래 데이터를 제외했다. Python 발췌에서는 로컬 경로와 작업 식별자를 제외했다. 원문과 공개용 요약을 같은 것으로 보이게 하지 않으며, 상세 페이지에도 같은 공개 방식을 반복 표시한다.

## 문장 작성 원칙

다음 표현은 공개 본문에서 피한다.

- `의사결정 표면` -> `작업 화면`
- `기획 계약` -> `기획 기준`
- `판단을 memory로 승격` -> `다음 작업에서 다시 쓸 기준으로 정리`
- `source binding` -> 본문에서는 `원본과 판단 기록을 연결`, 파일 안에서만 원어 유지
- `실행 gate` -> `실행 전 확인 단계`
- `production-complete` -> `완성 단계` 또는 현재 상태를 구체적으로 설명

한 문단에는 다음 네 가지를 모두 넣지 않는다.

`문제 + 도구 + 과정 + 한계 + 다음 단계`

본문은 질문과 결과를 먼저 쓰고, 도구와 경계는 표 또는 파일 발췌로 분리한다.

## 객관적 재평가

이전 지원 팩의 `포트폴리오 적합도 95/100`은 근거량을 과도하게 반영했고, 채용담당자의 읽기 시간과 문장 자연스러움을 충분히 반영하지 못했다. 아래 평가를 우선한다.

| 평가 항목 | 개편 전 | 개편 후 | 판단 |
| --- | ---: | ---: | --- |
| JD 핵심 요구와의 연결 | 84 | 92 | 여섯 섹션이 각 요구와 직접 연결됨 |
| 실제 근거 신뢰도 | 95 | 95 | 실제 레포와 공개용 발췌 기준 유지 |
| 3-5분 내 이해 가능성 | 66 | 91 | 시스템 목록을 줄이고 질문·결과 중심으로 변경 |
| 문장 자연스러움 | 68 | 88 | 추상적인 시스템 표현을 일반 언어로 변경 |
| 결과물과 과정의 균형 | 72 | 92 | INK 영상·이미지와 파일 발췌를 함께 배치 |
| 브랜드 직무로 읽히는 정도 | 74 | 87 | 실제 결과물을 Hero로 올리고 MUSINSA·ADSB 연결 |
| **공개 포트폴리오 종합** | **76** | **91** | **제출 가능한 수준** |

후보자 자체의 JD 핏은 `84/100`으로 유지한다. 포트폴리오 표현이 좋아졌다고 완료하지 않은 공간·리테일 경험이나 장기 조직 협업 역량이 새로 생기는 것은 아니다.

## 남은 약점

1. 완료된 리테일·공간 실험이 없다.
2. 동일 조건의 모델 비교 로그가 없다. 역할별 사용 근거로 대체했으며 모델 품질 우열은 주장하지 않는다.
3. 장기 조직 협업보다 개인 프로젝트 비중이 높다. MUSINSA 3인 팀, ADSB 산학, 교육조교 경험으로 보완한다.
4. Workbench는 개발 checkpoint이며 실제 곡 승인까지 검증되지 않았다.
5. One Move는 진행 중이므로 결과 영상이나 성공 문구를 넣지 않는다.

## 제출 판단

페이지 자체는 제출 가능한 수준이다. 다만 공개 배포 URL이 현재 개편본을 가리키는지와 비로그인 모바일 접근을 확인하기 전에는 지원서에 링크를 넣지 않는다. 최종 제출과 파일 업로드는 사용자 명시 승인 후에만 진행한다.
