## 1. 이 문서의 목적

이 문서는 원문 메모, GENTLE MONSTER 공식 JD, IDOL·Aurora·AHEYA 레포의 실제 기록을 한곳에 정리한 내부 편집 기준이다.

페이지에 모든 내용을 넣기 위한 문서가 아니다. 다음 세 가지를 구분하기 위한 소스북이다.

1. 실제로 확인된 사실
2. 지원자의 경험을 설명하는 해석
3. 공개 페이지에서 사용할 수 있는 표현

핵심 목표는 결과물이나 시스템 목록을 많이 보여주는 것이 아니라, 다음 질문에 답하는 것이다.

> 새로운 AI 변화를 어떻게 발견했고, 어떤 가능성을 보았으며, 무엇을 시험했고, 그 결과 제작 방식이 어떻게 달라졌는가?

팀워크는 이 개인 탐구 페이지에서 억지로 증명하지 않는다. MUSINSA 3인 팀과 ADSB 산학의 피드백 경험은 별도 프로젝트, 이력서, 자기소개서에서 담당한다.

완료하지 않은 리테일·공간 작업은 실적으로 쓰지 않는다. 마지막의 확장 방향에서만 제안할 수 있다.

## 3. 잘못 잡으면 안 되는 시작점

다음 문장은 제작 후반에 드러난 여러 문제를 시작부터 하나의 병목이었던 것처럼 합친다.

> 새로운 이미지·영상 모델이 빠르게 좋아지고 있었지만, 실제 제작에서는 프롬프트 입력보다 기획 기억, 얼굴 유지, 후보 선택, 장면 연결이 더 큰 병목이었습니다.

이 문장은 요약으로는 편하지만 실제 시작 동기와 다르다. 그대로 Hero의 문제 정의로 사용하지 않는다.

실제 시작점은 문제보다 **가능성의 발견**에 가깝다.

> AHEYA 마케팅 콘텐츠를 만들며 GPT Image API와 맥락을 공유한 생성 방식을 시험했습니다. 매번 한 장의 프롬프트를 다시 쓰기보다, 목적과 이전 판단을 AI와 이어 가면 한 사람이 반복 가능한 콘텐츠 제작 구조를 만들 수 있겠다고 생각했습니다.

그 뒤 실험의 규모가 커질 때마다 서로 다른 문제가 순서대로 드러났다.

- 짧은 콘텐츠의 양을 늘리는 것만으로는 반응이 계속 좋아지지 않았다.
- 창의적 판단까지 스크립트로 고정하면 비슷한 카메라·빛·포즈가 반복됐다.
- 얼굴 유지와 장면의 연속성은 별도 기준과 검토가 필요했다.
- 이미지와 영상 후보가 늘자 선택·배열·편집 관찰이 느려졌다.
- 실행이 빨라진 뒤에는 앞단 기획이 흔들릴 때 버리는 결과가 더 많아졌다.

따라서 현재의 결론은 다음과 같이 쓴다.

> 반복 실행은 자동화할 수 있었지만, 자동화할수록 가장 중요한 일은 기획의 방향과 선택 기준을 분명히 하는 것이었습니다. 그래서 생성은 빠르게 반복하되 메시지·톤·선택·승인은 제가 맡고, 실패와 판단은 다음 제작에서 다시 쓸 수 있도록 남기는 구조로 바꿨습니다.

## 4. 핵심 포지셔닝

### 메인 포지셔닝

> 새로운 AI 변화를 실제 콘텐츠 제작에 붙여 보고, 성공과 폐기에서 얻은 판단을 다음 제작 방식으로 바꾸는 AI Creative Explorer

### Hero용 문장

> 새로운 AI를 발견하면, 기능을 소개하는 데서 멈추지 않고 제가 만들고 있는 콘텐츠에 직접 붙여 봅니다.

### 핵심 질문

> 기획의 맥락을 AI와 공유하고 반복 작업을 자동화한다면, 한 사람이 운영하는 제작 스튜디오는 어디까지 확장될 수 있을까?

### 앞부분에서 먼저 제시할 결론

> 자동화할수록 병목은 실행에서 기획과 판단으로 이동했습니다. 반복은 시스템에 맡기고, 메시지와 감각을 결정하는 일은 직접 남겼습니다.

### 피해야 할 포지셔닝

- AI 자동화 엔지니어
- LLMOps 또는 ML 연구자
- 완전 자동화된 스튜디오를 완성한 사람
- 여러 모델의 성능을 동일 조건에서 비교한 사람
- 비용만 줄이기 위해 유료 도구를 피한 사람

## 5. 실제 탐구의 출발과 변화

### 5.1 AHEYA에서 콘텐츠로

**사용자 진술**

- AHEYA는 AI builder를 위한 크라우드펀딩과 신뢰 기록을 탐구한 개인 서비스였다.
- Solidity 스마트계약, wallet·Trust API, 외부 개발 인프라를 AI와 함께 파고들었다.
- 약 2~3주 동안 X에서 직접 접촉했지만 유효한 시장 반응을 얻지 못해 빠르게 중단했다.
- 마케팅용 이미지와 10초 안팎의 짧은 클립을 만들다가 반복 가능한 콘텐츠 제작 구조에 관심이 옮겨 갔다.

**공개 표현**

> AHEYA를 알리기 위해 이미지와 짧은 영상을 만들던 중, 생성 기능을 일회성 결과가 아니라 반복 가능한 제작 구조로 연결해 보기 시작했습니다. 콘텐츠의 양만 늘리는 방식은 반응을 지속시키지 못했고, 하나의 메시지와 톤을 가진 긴 형식으로 실험을 옮겼습니다.

### 5.2 Aurora: 반복 제작 가능성

**레포 확인 사실**

- Aurora V1은 이미지·영상 프롬프트, 리서치, 검토, 게시, 분석을 한 구조에서 다뤘다.
- V1은 생산적이었지만 active canon을 혼동하기 쉬워 2026-05-15에 archive로 보존됐다.
- V2는 조사 → 선정 → 패킷 → 생성 → 사람 검토를 분리했다.
- 13개 MV와 13개 STAGE 제작 단위를 운영했다.
- 실제 M01·M11 MV/STAGE 통과 보드와 identity reference가 남아 있다.

**판정**

> 같은 얼굴을 유지하며 서로 다른 장면을 반복 제작할 수 있다는 가능성은 확인했습니다. 하지만 창의적 판단까지 고정하면 결과가 비슷해졌습니다. 이후부터 반복 정보와 창의적 판단을 분리했습니다.

### 5.3 실제 제작 순서

레포 날짜로 확인한 순서는 다음과 같다.

1. `Root Signal` — 2026-05-24 run, 2026-05-29 v11 final closeout
2. `LOW` — 2026-05-26 run, 2026-06-11 discard/archive state
3. `Pulso` — 2026-06-11 run, 2026-06-18 final completion
4. `Left in That Night` — 2026-06-14 run, 2026-07-06 formal discard
5. `INK` — 2026-06-18 run, final master와 공개 메시지 등록
6. `Front Planning Workbench` — 2026-07 개발 checkpoint

`LOW`와 `Left in That Night`를 하나의 실패 묶음으로 쓰지 않는다. 두 작업은 드러낸 문제와 남긴 규칙이 다르다.

### 5.4 Root Signal: 첫 전체 제작과 편집 기록

**레포 확인 사실**

- v11 final master까지 11개의 편집 버전과 QC 기록이 남아 있다.
- 37개 source를 사용했고 final recipe에서 missing source는 0이었다.
- 최종 결과는 이전 렌더를 다시 재료로 쓰지 않고 원본 source로 되돌아가 3:2 master를 만들었다.
- edit review와 closeout에서 source keeper, QC, package, social source policy가 다음 harness 규칙으로 승격됐다.

**포트폴리오에서 말할 것**

> 첫 전체 MV를 완성하며, 생성보다 편집 판단을 기록하는 일이 다음 제작에 더 중요하다는 것을 배웠습니다. 통과한 컷도 이전 렌더에 묻어 두지 않고 원본 source와 선택 이유를 다시 찾을 수 있게 했습니다.

### 5.5 LOW: 얼굴 유지와 기계적인 편집

**레포 확인 사실**

- LOW의 face-only reference 활용은 멤버 인지도를 유지하면서 표정과 시선은 현재 장면에 맞게 생성하는 규칙으로 남았다.
- 기계적인 beat grid 편집은 founder review에서 거절됐다.
- lyric/rhythm accent, body landing, camera carry, motion continuity를 함께 보는 편집 기준이 남았다.
- LOW는 active production에서 폐기돼 archive-only로 남았다.

**포트폴리오에서 말할 것**

> LOW에서는 얼굴 레퍼런스가 정체성을 붙잡는 데 유효했지만, 비트 위치만 따라 자른 편집은 음악과 영상이 따로 움직였습니다. 이후 분석값은 관찰에만 쓰고, 컷은 몸의 동작·카메라의 이어짐·보컬의 진입을 함께 보도록 바꿨습니다.

### 5.6 Pulso: 프레임·비트 기반 제작 흐름

**레포 확인 사실**

- 곡 구간 분석, reference 영상 contact sheet, keyframe packet, 03V video prompt, playback review, edit marker plan이 연결돼 있다.
- YouTube final과 TikTok inbox upload 기록까지 closeout됐다.
- face reference policy, audio-frame placement, section playback QC가 실제 run에 남아 있다.

**포트폴리오에서 말할 것**

> Pulso에서는 곡을 구간으로 나누고, 각 구간의 이미지·영상 후보를 프레임과 비트에 맞춰 검토했습니다. 생성, 동작, 편집을 한 번에 자동 결정하지 않고 서로 다른 검토 단위로 나누자 전체 곡을 끝까지 연결할 수 있었습니다.

### 5.7 Left in That Night: 모티브가 많아도 이야기는 생기지 않는다

**레포 확인 사실**

- 2026-07-06 full MV route가 공식 폐기됐다.
- 여러 모티브와 공간, 레퍼런스가 있었지만 founder는 보드를 서로 연결되지 않은 재료로 판단했다.
- 이후 이미지 보드 확장 전 emotional owner, concrete action, cause-and-effect, motif job, 30-second proof route를 먼저 검증하는 규칙이 추가됐다.

**포트폴리오에서 말할 것**

> Left in That Night에서는 레퍼런스와 모티브를 많이 모았지만, 그것들이 다음 장면을 일으키는 원인이 되지 못했습니다. 더 생성하는 대신 작업을 폐기했고, 이후에는 감정의 주인·보이는 행동·장면의 인과를 보드보다 먼저 확인합니다.

### 5.8 INK: 메시지와 시각 시스템의 결합

**레포 확인 사실**

- 공개 메시지는 `Never quit. Reject someone else's script. Keep writing outside the page.`로 정리돼 있다.
- 4명의 멤버, 13개 곡 구간(S00-S12), 인물별 object system, 공간·카메라·의상·행동이 track board에 연결돼 있다.
- reference function mining, selected-audio analysis, lyrics direction bridge, high-density storyboard, contact sheet, output registry가 남아 있다.
- final master가 존재한다.

**포트폴리오에서 말할 것**

> INK에서는 “남이 정한 선 밖으로 계속 나아간다”는 메시지를 먼저 고정하고, 네 멤버의 행동·오브젝트·공간 변화가 그 메시지를 보이도록 설계했습니다. 곡의 13개 구간별 후보를 컨택트시트로 묶고, 얼굴·인과·카메라·빛·다음 장면으로의 연결을 기준으로 골랐습니다.

### 5.9 Workbench: 기획하는 사람도 병목이 될 수 있다

**레포 확인 사실**

- status는 `runnable development checkpoint`다.
- Live Front Planning, reference/frame intake, visual canvas, Sequence Rail, founder selection/hold/reject, contact sheet, explicit founder review를 제공한다.
- 생성 API를 자동 실행하는 제품이 아니다.
- 생성된 후보보다 plan과 founder decision을 먼저 다룬다.
- real-song production acceptance를 완료한 제품으로 주장하지 않는다.

**포트폴리오에서 말할 것**

> 실행이 빨라진 뒤에는 제가 기획을 바꾸거나 이전 판단을 잊는 일이 더 큰 낭비가 됐습니다. 그래서 레퍼런스의 역할, 곡 구간, 후보 상태, 보류 이유를 한 화면에서 조립하고 다음 단계에 넘기는 Workbench를 만들었습니다.

## 6. 최신 AI 변화 탐색을 보여주는 세 개의 기록

일반적인 `발견 → 질문 → 시험 → 판정` 설명을 별도 방법론으로 길게 쓰지 않는다. 실제 사례마다 같은 네 칸을 사용한다.

### 기록 A. 맥락을 이어 가는 LLM과 CLI

**발견과 문제**
AHEYA를 AI와 개발하면서, 짧은 프롬프트보다 목적·이전 결정·현재 상태를 함께 공유할 때 의도를 더 오래 유지할 수 있다는 가능성을 보았다. 반면 창의적 의미까지 스크립트로 고정하면 결과가 반복됐다.

**질문**
매번 처음부터 설명하지 않으면서도, 작업마다 다른 메시지와 감각을 남길 수 있을까?

**시험**
Codex와 Grok에 곡 구간, reference function, 선택·보류 이유를 공유했다. 파일 탐색, 누락 검사, 상태 갱신은 skill·registry·script로 분리했다.

**판정**
`채택` — 창의적 의미는 대화와 사람 검토에 남기고, 반복 가능한 상태 정보만 구조화한다.

### 기록 B. 이미지·영상 생성 모델과 API

**발견과 문제**
이미지·영상 생성이 빨라지며 한 인물의 얼굴을 유지한 채 서로 다른 장면과 움직임을 전개할 가능성이 커졌다. 다만 세션과 API를 무조건 연결하면 비용과 통제 범위가 커진다.

**질문**
하나의 identity를 유지하면서 13명의 서로 다른 MV·STAGE 장면을 반복 제작할 수 있을까?

**시험**
Loom의 얼굴 reference를 기준으로 Aurora V2에서 13 MV·13 STAGE 제작 단위를 운영했다. 세션에서 먼저 시험하고, 반복이 확인된 구간만 API와 script로 옮겼다.

**판정**
`부분 채택` — 반복 실행에는 유효했다. 얼굴 기준, 최종 선택, 유료 실행은 사람 승인 단계로 남긴다.

### 기록 C. 편집·미디어 분석을 로컬 작업으로 분해

**발견과 문제**
Premiere Pro·After Effects·CapCut, ComfyUI, Grok Imagine의 기능을 보며 완성형 앱보다 실제 제작에서 필요한 작업 단위를 먼저 보게 됐다. 후보가 늘자 컷 선택과 연결 확인이 느려졌다.

**질문**
전문 편집기를 복제하지 않고도 후보 비교, roughcut, QC에 필요한 부분만 만들 수 있을까?

**시험**
ffprobe·OpenCV·librosa로 source, frame, motion, beat를 읽고, ffmpeg로 contact sheet와 roughcut을 만들었다. 이후 Source/Program monitor, timeline, marker, waveform을 가진 Python/Tk Edit Desk를 시험했다.

**판정**
`부분 채택` — 분석값과 로컬 도구는 관찰 속도를 높인다. 좋은 컷과 타이밍을 자동 판정하지는 않으며 Edit Desk는 backlog 상태의 보조 MVP로만 공개한다.

### 별도 기록 D. OpenClaw Yui와 Trust API

이 기록은 IDOL production harness의 근거로 섞지 않는다. AHEYA의 별도 서비스 탐구로 둔다.

**질문**
AI agent가 후보 탐색, 계획, 실행, 검토, 신뢰 기록을 지속적으로 이어 갈 수 있을까?

**시험**
OpenClaw Yui에서 queue·scheduling·strict review·Trust API 기록을 연결했다.

**판정**
`중단` — 실행 구조는 만들었지만 시장 반응, 외부 생태계 변화, 유지 비용을 고려해 서비스 확장을 멈췄다. 자율 거래 성과나 상용 배포는 주장하지 않는다.

## 7. 최종 페이지 정보 구조

### 00. HERO / 결론부터

첫 화면과 다음 한 화면 안에서 네 가지가 보여야 한다.

- 누구인가: 새로운 AI 변화를 콘텐츠 제작에 직접 붙여 보는 사람
- 무엇을 물었는가: 한 사람이 운영하는 제작 스튜디오를 어디까지 확장할 수 있는가
- 무엇을 만들었는가: INK, Loom, Aurora 26 units, Workbench, decision archive
- 무엇을 배웠는가: 자동화할수록 기획과 판단이 중요해졌다

INK의 강한 이미지 또는 짧은 영상 proof를 첫 화면에서 보여준다. 전체 결과 설명은 04에서 한다.

### 01. ORIGIN / 가능성은 어디서 시작됐나

질문형 제목:

> 마케팅용 이미지 한 장은 어떻게 한 사람의 제작 스튜디오라는 질문으로 커졌을까?

구성:

`AHEYA marketing content → context-aware generation → short clips → Aurora 26 units → full MV hypothesis`

이 섹션은 한 화면 안에 끝낸다. AHEYA 스마트계약 상세는 넣지 않는다.

### 02. TREND LOG / 새 기능에서 무엇을 발견하고 어떻게 판단했나

질문형 제목:

> 새 기능이 나올 때마다, 무엇을 실제 제작에 붙여 봤을까?

세 기록을 각각 다음 순서로 보여준다.

`발견과 제작 문제 → 질문 → 시험 → 판정(채택/부분 채택/보류) → 다음 구조`

도구명을 제목으로 쓰지 않는다. 제작 질문을 제목으로 쓰고 도구명은 근거 라벨로 내린다.

### 03. ITERATION / 실패는 다음 작업을 어떻게 바꿨나

질문형 제목:

> 한 편을 끝낼 때마다, 무엇을 버리고 무엇을 다음 규칙으로 남겼을까?

실제 순서:

`Root Signal → LOW → Pulso → Left in That Night → INK → Workbench`

각 항목은 세 줄만 사용한다.

- 이번에 시험한 것
- 드러난 한계 또는 통과한 판단
- 다음 작업에서 바뀐 것

긴 파일 설명이나 여러 실패를 한 문장에 합치지 않는다.

### 04. OUTCOME / 그래서 무엇이 남았나

질문형 제목:

> 반복 실험은 어떤 콘텐츠와 도구, 기록으로 남았을까?

이 섹션에서 결과를 네 묶음으로 보여준다.

1. **CONTENT — INK**: final video, 메시지, reference → 후보 → 선택 → final
2. **EXPERIENCE — Loom**: 13 identities, tracks, short content, local interaction prototype
3. **PRODUCTION — Workbench + Edit Desk + harness**: 사람이 판단하고 AI가 반복 실행하는 구조
4. **MEMORY — archive + decision log + X/TikTok review loop**: 실패와 플랫폼 신호를 다음 실험에 넘기는 방식

기술 구조는 이 결과를 증명하는 범위에서만 보여준다. 전체 stage registry나 skill 전문은 공개하지 않는다.

### 05. SERVICE EXPLORATION / AHEYA

AHEYA는 별도 부록 성격으로 한 화면에 정리한다.

`Crowdfunding → Trust API → OpenClaw Yui → 중단 판단`

목적은 개발 능력 자랑이 아니라, 비개발 전공자가 관심이 생긴 기술을 서비스 수준까지 집요하게 파고든 증거다.

### 06. CLOSING / 가져갈 세 가지

- 새 기술을 실제 제작 질문으로 바꾸는 관점
- 가능성을 콘텐츠·도구·서비스 프로토타입까지 시험하는 실행력
- 성공과 폐기의 판단을 다음 사람이 다시 읽을 수 있게 남기는 기록 방식

공간·리테일은 완료 실적으로 쓰지 않는다. 다음 문장처럼 확장 방향으로만 말한다.

> 입사 후에는 이 탐구 방식을 콘텐츠에만 한정하지 않고, 웹 인터랙션과 공간 프로토타이핑에서도 작은 실험으로 먼저 검증하고 기록하겠습니다.

## 8. 페이지를 나열식으로 보이지 않게 하는 편집 규칙

1. 섹션마다 주장 하나만 둔다.
2. 문단보다 `질문 → 시험 → 판정 → 다음 변화`의 시각적 관계를 먼저 보여준다.
3. 파일은 독립된 전시물이 아니라, 바로 위 주장에 붙는 증거로 배치한다.
4. 결과물은 초반에 teaser로 보여주고 04에서 전체 맥락과 함께 설명한다.
5. 같은 핵심을 `역설계`, `아키텍처`, `하네스`, `production system`으로 반복하지 않는다.
6. 숫자는 의미가 있을 때만 쓴다. `13 identities`, `13 MV + 13 STAGE`, `8 phases / 29 stages`의 역할을 설명한다.
7. 긴 코드 전문 대신 판단을 보여주는 6~12줄만 발췌한다.
8. 각 판정에는 `채택`, `부분 채택`, `보류`, `폐기`를 명시한다.
9. “완성하지 못했다”를 반복하지 않는다. 한계는 해당 실험의 판정에만 적는다.
10. 한 화면에 본문 2~3문단을 넘기지 않는다.

## 9. 표현 기준

### 사용할 표현

- 맥락을 공유했다
- reference의 역할을 정했다
- 곡 구간별로 후보를 묶었다
- 통과·보류·폐기 이유를 남겼다
- 반복 실행과 창의적 판단을 분리했다
- 실제 사용 역할을 나눴다
- 플랫폼 지표를 다음 검토 후보로 사용했다
- 메시지와 감각은 직접 판단했다

### 줄이거나 피할 표현

- AI 도구를 역설계했다
- AI가 저와 똑같이 생각하게 했다
- 완전 자동화했다
- 스튜디오를 완벽히 대체했다
- 환각률이 낮다
- 성능이 압도적이다
- 구독 비용을 피했다
- 우리만의 비밀, 영업기밀
- 저 도구를 왜 돈 내고 써야 하나

비용은 다음처럼 바꾼다.

> 여러 유료 기능을 그대로 추가하기보다, 실제 제작에서 필요한 작업 단위를 먼저 나누고 기존 세션·API·로컬 도구로 반복 가능한지 시험했습니다.

모델 비교는 다음처럼 한정한다.

> 동일 조건의 우열 비교가 아니라, 실제 작업에서 각 도구가 맡은 역할과 통제 범위를 기록했습니다.
